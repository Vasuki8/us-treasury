# Census source checks and alert verification

User request: make automatic Census housing/retail checks and their GitHub alerts reliable, preserving the current UI and colors. Baseline `904bc57` has 217 captures. This delivery changes only collection retry classification and alert evidence selection, with no source definition, numeric observation, immutable capture, CSS or layout changes.

## Root causes and small fixes

The housing bulk endpoint returned HTTP 520. The shared HTTP helper recognized several transient server statuses but omitted 520, so the configured three attempts stopped after one. The existing helper now recognizes 520 alongside its other statuses. Trusted collection still has at most three attempts, 5/30-second backoff, a 60-second cumulative wait budget, unchanged 45-second request deadlines and unchanged byte limits. Persistent errors still fail; redirected failures are not retried, and denial, invalid content/schema and oversized data still fail normally. Retail timeouts already followed bounded retries; no longer deadline or replacement economic measure is introduced. [Cloudflare's 520 documentation](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-5xx-errors/error-520/) identifies an empty, unknown or unexpected origin response.

Both existing official Census ZIP routes returned HTTP 200 twice, without redirects, in 120–372 milliseconds. Their complete files exactly match the last verified Census capture hashes: MARTS `5a403391d7f15ca1a23080ba095ff5dba6a9220f23323704d7458178962c6589`, RESCONST `b8bb28bdc72868c4dba5d213f9a518e411fcd34cfaa4145613768ca2bb5940de`. All 417 retail, 813 starts, 801 permits and 705 completions observations, raw values, baselines, notes, identifiers, units and attribution compare exactly; unchanged parsers and commercial-data admission pass. Parsing/collection from downloaded bytes took about 80–109 ms, ruling out parser work as the 45-second network deadline cause. Official API alternatives require credentials and no-key probes redirected to missing_key.html; keeping the working approved bulk feeds is the supported minimal approach.

The alert issue followed a partial rerun of workflow 40449744686. It retained two nonexpired `official-source-check-status` artifacts: ID 12710440122 at 04:28:28Z and ID 12710069547 at 04:46:33Z. The reader rejected multiple matches before downloading either. The newer ID is smaller, so ID sorting would be incorrect. The selected source job actually ran 04:42:22Z–04:46:35Z. The corrected caller supplies that actual job, and the reader selects the unique upload in its time window and validates checkedAt against the same job. A missing, expired, contradictory or ambiguous current upload cannot substitute an older success. Inherited successful jobs retain their own original timestamps during partial reruns, so their unchanged reports remain correctly attributable. Existing trusted-main checks, exact schemas, compressed/decompressed byte limits, safe redirect allowlist, download deadline and credential stripping remain intact.
