# Snapshot loading and immutable archive storage

Optimize the existing Meridian static application; preserve Graphite, observations, data rights/admission, provenance, all retained capture objects, ordering, as-known cutoffs, revision confirmations, source terms and CSV values. No credentials, paid services, dependencies or new infrastructure. Keep unrelated exports/ untouched. The user's explicit optimization/test/push request and prior autonomous milestone instruction authorize implementation and delivery.

Measured baseline: generated source 15,047,274 bytes; compact current payload 6,218,032 bytes; archive 4,079,805 bytes, 25 captures. Startup scans all 48 revision series (~162ms locally). Thirteen confirmation captures are legitimate knowledge/provenance, not disposable duplicates. A matching unchanged daily refresh appends about 17KB of compact capture facts. Treasury URL repetition dominates the initial archive.

Store each original capture as a content-addressed immutable gzip JSON file under src/history/. The ordinary generated snapshot contains only current data and an ordered archive index. Pool repeated long string literals in generated JavaScript using a lossless serializer; do not change the semantic schema or observation records. Existing capture contents and identities must compare exactly after migration. Do not alter the pure v1 replay model.

Write/verify immutable files first and replace only the generated root last, using atomic rename. Existing archive files may never be modified or deleted. A failed write can leave an unreferenced file, but cannot replace the previous root with dangling references. Publication accepts only the root and exact newly referenced immutable files; it verifies the prior ordered prefix, content hashes, and all historical data admissions while preserving existing expected-HEAD, index, remote-race and normal-push safeguards.

Build and local server hydrate and validate full history before projecting public assets. Emit a current-only browser module plus one content-addressed archive bundle in gzip and plain JSON fallback forms, all within the same content-versioned deployment. Browser module includes only a compact bundle descriptor. Load via same-origin fetch only for Revision history or an indicator's Revisions tab. Gzip uses native DecompressionStream where supported, with a plain JSON fallback; verify lengths, SHA256 and v1 shape. No archive fetch or history scan on ordinary startup.

Use explicit idle/loading/ready/error state, one in-flight load, cached success, explicit retry after failure, memoized per-series revisions, accessible loading/error messages and disabled CSV until ready. Preserve routes, cutoff inputs, focus and scroll through completion; ignore late results on other routes. Empty verified history differs from unavailable history. Do not substitute latest data after a history load failure.

Verify all existing capture objects, every capture cutoff and one millisecond before it, all registered revision histories, metadata changes/tombstones, unchanged confirmations, terms and CSV equality. Test corruption/missing files, admission of historical-only data, write-before-root failure, publisher scope/races, gzip/fallback loading, failure/retry and navigation races. Smoke/live verifiers must explicitly discover both lazy bundle files. Measure before/after payload and unchanged-refresh growth, then test desktop/mobile/keyboard and deployment.
